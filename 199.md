## 7. What I think we should do next — max detail

### 7.1 Enforce API key scopes (critical gap, ~2h)
What is wrong today:
- `backend/app/api/api_keys.py` stores `scopes` (e.g. `["read"]`) on the ApiKey row, but nothing checks them. Any valid key can call any endpoint the owning user can call. That means a read-only key you give to an accountant can still POST transfers if the user can.
- `authenticate_by_api_key()` returns User but drops scopes, so downstream `get_current_user` callers lose the scope context.

What to build:
1. Define canonical scopes: `read`, `write`, `banking:read`, `banking:write`, `qubo:read`, `qubo:write`, `admin`.
2. In `authenticate_by_api_key()`, return `(User, ApiKey)` or stash `request.state.api_scopes`. Simplest: add `get_current_api_key()` dependency and a `require_scope("banking:write")` dependency similar to `require_role()`.
3. Method → scope mapping: GET = `*:read`, POST/PUT/PATCH/DELETE = `*:write`, with per-router prefix (`/api/banking/*` → `banking:*`, `/api/qubo/*` → `qubo:*`).
4. On scope failure return 403 `{"detail":"insufficient_scope","required":"banking:write"}` so API consumers can handle it programmatically.
5. Frontend: add Settings → API Keys page (list + create + copy-once + revoke + rotate). Today keys are API-only, so no non-technical user will discover them.
6. Tests: `backend/tests/test_api_keys.py` — create key, use X-API-Key to GET banking overview (200), POST transfer with read-only key (403), rotate (old 401, new 200), revoke (401), expired key (401).

Acceptance: read-only key cannot mutate; scopes visible in list endpoint; docs show X-API-Key usage.

### 7.2 Replace in-memory rate limiter with Redis (blocks multi-worker prod, ~4h)
What is wrong today:
- `PerUserRateLimitMiddleware` + `RateLimitMiddleware` + `ThreatDetectionMiddleware` all keep counters in process memory (`defaultdict(list)` + `threading.Lock`). With gunicorn `-w 4` or 2 containers, each process has its own counter, so effective limit is 4x advertised. Restart wipes counters. No shared view of abuse.
- No `Retry-After` consistency across instances. No dashboard.

What to build:
1. Add `REDIS_URL` to `backend/app/config.py` (default empty = in-memory fallback for dev/test).
2. New `backend/app/security/redis_rate_limit.py` with `redis.incrby + expire` sliding window, key `rl:{client_id}:{minute_bucket}`. Use Lua or pipeline for atomic incr+expire.
3. Keep current class as fallback when redis unavailable; log warning once.
4. Add per-plan limits loaded from subscription row, not hardcoded PLAN_LIMITS. Free 60, Pro 300, Enterprise 1000 is fine as default, but read override from DB when `request.state.subscription_plan` is set by auth.
5. Add `/api/admin/rate-limit/status` (admin only) showing top offenders from Redis `ZSET`.
6. Load test: `scripts/load_test_rate_limit.py` — 200 rps for 60s against staging, assert 429 rate < 5% for pro key, > 90% for anonymous flood.

Acceptance: kill -9 one worker, counters survive; 2 workers enforce single global limit.
